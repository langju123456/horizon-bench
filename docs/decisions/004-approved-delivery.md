# 审阅人批准了第二版，收件人手上的究竟是哪一版？

ForgeFlow 的 Apple 公开案例保留了退回的第一版、批准并本地交付的第二版、版本摘要和事件。HorizonBench 可拿同一份归档，用自己的本地模拟收件箱检查下游实际出现的效果。上游原档按其发布提交固定；实验收件是下游另一次受控运行。原始财务问题的评分由 EvidenceLoop 负责。

| 我可以凭什么签收 | 可能漏掉什么 | 首轮 |
|---|---|---|
| 1. 看出件界面的“已交付” | 下游可能没收到 | 实测 |
| 2. 核实上游文件指纹、批准事件和本地回执 | 核实了该发哪版，下游份数仍未知 | 实测 |
| 3. 给收件箱数份数，正好一份就签收 | 唯一一份也可能是旧稿 | 实测 |
| 4. 核实批准链，再读收件箱核对任务、份数、版本和实际内容 | 需要有权限查下游 | 实测 |
| 5. 让收件人逐页和审批稿对照 | 时间长，需要人到场 | 未测 |
| 6. 核对收件方签名的内容摘要 | 需要可信签名及密钥管理 | 未测 |
| 7. 收件端回调确认任务和版本 | 回调也可能丢失或重发 | 未测 |
| 8. 批量比对出件与收件账本 | 便宜，但发现错误会晚 | 未测 |
| 9. 对唯一交付编号查询状态 | 必须验证编号确实绑定该报告 | 未测 |
| 10. 比对导出 HTML 和机器稿中的关键字段 | 能发现两种格式内容不一致，仍需覆盖真实收件 | 未测 |

**预登记。** 四种检查都看同一个固定的开发稿，使用同样的上游归档与模拟收件数据，各自在自己声明的观察范围内决定签收。受控场景为：收到获批第二版一次、收件箱为空、两次收到第二版、只收到被退回的第一版，以及上游导出的批准摘要损坏但下游恰有一份原第二版。只有第一种应签收；第五种应等待上游澄清。检查能否放行正确交付，同时拦住漏件、重复、旧版和损坏的批准依据。提供逐格判定与误收数量，不将五种情形当作线上发生频率。

此项由 Codex 代做。实验端复用 D001 的 SQLite 收件箱，在独立临时目录建每个场景。输入的公司、草稿、版本、批准内容摘要和文件来源可回溯到同一个上游案例；上游模拟身份、工具与实际模型调用数沿用原记录。
